# Template marketplace

- **Status:** M1 built (public browse pages). M2 and M3 are design, not code.
- Decided by [ADR-0012](../adr/0012-a-brokered-template-marketplace.md)
  (Accepted 2026-10-13). A listing is a template as [`templates.md`](templates.md)
  defines it. Running one is a job ([`job-api.md`](job-api.md)), billed like
  any other ([`metering.md`](metering.md)).

## M1 — public browse (built)

Two static pages on compute.unifyai.us, generated by `vinext build` from
`compute-api/config/templates.json` and `compute-api/config/skus.json`
(`app/marketplace/catalogue.ts`):

| Route | Shows |
|---|---|
| `/marketplace` | Every template, available first and then by id, as a card: title, a short description, the GPU of its default SKU, its default runtime, and whether it can run today |
| `/marketplace/<id>` | One template in full: description, publisher, GPU, default runtime, declared inputs and outputs, what a submit may override, the image with its digest, licence and source, and the `POST /compute/v1/jobs` call that runs it |

Rules the pages follow, held by `deploy/site/smoke.sh`:

- **Availability is computed the way compute-api computes it.** A template is
  available only if it is declared available *and* its default SKU is
  available. Otherwise the page shows the template's own reason, or names the
  SKU.
- **No prices.** `skus.json` prices are placeholders (its `note`), and
  AGENTS.md forbids site copy that promises pricing. The pages name the GPU,
  never a rate.
- **The publisher is always "Unify Compute"** (ADR-0012, decision 2).
- **The run example is only valid if submit accepts it.** It names the
  template and gives one `source` per declared input mount, nothing else. Each
  source URL ends in the file name the input's description names, because the
  run step saves under the URL's last path segment (`templates.md`).
- The early-access note from `/start` applies here too: running needs an
  account with compute enabled.

A change to either JSON file changes these pages, so it needs a site release
as well as an API release (ADR-0012, *Consequences*).

## M2 — account listings (built; open on staging only)

Built in `compute-api/internal/listings` (store and rules), the dashboard
routes below, and `compute-api admin listing …`. It ports Unify Data's
brokered market (its ADR-0011: `products.review_state`, `reviewed_by`,
`listed`, a reason on every decision, rejection unlists, the seller never
crosses to the buyer) onto compute's tables. Account listings are **closed
in production** (`ENVIRONMENT=production`): `GET /templates` serves none and
`admin listing approve` refuses, until ADR-0012 §4 holds. Submitting,
editing, unlisting and the queue work everywhere, so the flow is exercised
on staging first.

### Store

```sql
CREATE TABLE listings (
  id            text PRIMARY KEY,           -- lst_<ulid>
  account_id    bigint NOT NULL REFERENCES accounts(id),
  template_id   text NOT NULL UNIQUE,       -- the slug buyers submit; may not collide with templates.json
  template      jsonb NOT NULL,             -- one templates.json entry, validated by internal/template
  review_state  text NOT NULL CHECK (review_state IN ('pending','approved','rejected')),
  review_reason text,
  reviewed_by   text,
  reviewed_at   timestamptz,
  listed        boolean NOT NULL DEFAULT true,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);
```

A listing is visible to buyers when `listed AND review_state = 'approved'`.
Validation is `internal/template`'s, unchanged. A listing that would not boot
as a curated template cannot be submitted. Approval also checks the
`image_source` the publisher gave against decision 4 of ADR-0012.

### Routes

| Route | Who | Effect |
|---|---|---|
| `GET /dashboard/v1/listings` | session | The caller's listings, with review state and reason, and run counts once jobs record their template id |
| `POST /dashboard/v1/listings` | session, compute enabled | Submit; `pending` |
| `PATCH /dashboard/v1/listings/{id}` | session, owner | Replace the template; the listing is relisted and returns to `pending` whatever changed (a relisting after an unlisting is a new request, as in Unify Data). The template id cannot change |
| `POST /dashboard/v1/listings/{id}/unlist` | session, owner | `listed = false`; never refused |
| `GET /compute/v1/templates` | public | Approved, listed account listings join the curated ones where the deployment is open; every entry gains `publisher: "Unify Compute"` (an additive field). A submit may name an approved listing's id |

### Admin CLI

```
compute-api admin listing queue
compute-api admin listing show <id>
compute-api admin listing approve <id> --reason TEXT
compute-api admin listing reject <id> --reason TEXT
compute-api admin listing unlist <id> --reason TEXT
```

As with every mutating admin verb, each one writes its change and an
`audit_events` row in one transaction.

### What the first review must check by hand

`admin listing show` prints the template as buyers would see it and the
`image_source` the publisher gave. Approval is the reviewer attesting to
ADR-0012 §4: nothing checks the image's source automatically.

### Before M2 reaches production

- ~~Jobs record `template`~~ Done: `jobs.template_id`, set on every template submit; listings count runs by it.
- One of ADR-0012 decision 4's two conditions holds: egress control, or
  images built from reviewed source.

## M3 — dashboard (design)

- **Browse** in the app: the same cards, plus a "Run this" form. The form
  collects one `source` per input and every overridable field the template
  allows, then submits with the session to a `/dashboard/v1` route.
- **My listings**: submit, edit, unlist, and see review state with the
  reviewer's reason.

## Not planned

Seller fees, payouts, ratings, reviews, comments, and publisher profiles.
Each needs a new ADR (ADR-0012 §3).
